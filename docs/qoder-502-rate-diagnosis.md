# 诊断：Qoder 请求「速率快、老 502、被上游拒绝」

排查时间：2026-10-11
现象（用户描述）：qoderToken 速率快，经常 502，疑似限额被上游拒绝。

## 结论：不是上游限流。是三个本端问题叠加。

实测证据（全部走装配后的 profile 路径，用真实凭据打真实上游）：

| 实验 | 结果 |
|---|---|
| 串行 12 次 | **12/12 全 200**，耗时 424–1704ms |
| 并发 6 路 | **6/6 全 200** |
| 并发 12 路 | **12/12 全 200**，最长 1433ms |
| 长回复（600 字） | 200，但**总耗时 5124ms**、响应 35.1KB |
| 短回复 | 200，440ms、1.3KB |
| **直连上游拆 TTFT** | **首字节 421ms / 收完 5295ms** |

最后一行是决定性的：上游**首字节只要 421ms**，但插件把 5.3 秒全缓冲完
才交给客户端 —— **把 421ms 的可流式响应，人为变成了 5.3 秒的首字节等待**。
上游从未限流。18 次并发压测零失败、零 429、零 5xx。
所以「限额上游拒绝」这个判断不成立 —— 真正的问题在插件这一侧。

---

## 问题一（主因）：整个 SSE 流被完整缓冲后才回给客户端

`lib/qoder-relay.mjs:343` 的 `sendQoderRequest` 把响应读干：

```js
const chunks = [];
res.on('data', (c) => chunks.push(c));
res.on('end', () => resolve({ status, text: Buffer.concat(chunks).toString('utf8') }));
```

**没有任何一帧会在流进行中被转发。** 长回复实测 5.1 秒全部积压在内存，
客户端这 5 秒里收不到任何东西。

这不是可以顺手改掉的疏忽 —— 它是两个**刻意的设计**逼出来的：

1. `extractInnerBody(text)`（`lib/qoder.js:119`）要先看到完整 text 才能判断
   「HTTP 200 但业务失败」；
2. `sseStreamOf(upstreamText)`（`lib/qoder.js:248`）是同步遍历整个字符串。

### 为什么这会表现成「502 / 被拒绝」

DSH → pi-ai 的 `streamIdleTimeoutMs` 是 **300000ms**（5 分钟），本身够宽，
但**首字节延迟**（TTFT）被拉到了「整个回复生成完」那么长。任何一层
（pi-ai、DSH 宿主、用户的代理）只要按首字节计时，长回复就会被判超时并
**重发请求** —— 而客户端重发 = 又一次完整的上游调用。

这条链解释了「速率快」：**同一个回答在上游被要了不止一次**。

## 问题二：一次用户请求最多放大成 3 次上游调用

`lib/qoder.js:397`：

```js
const attempts = Math.max(1, Math.min(3, pool.list().length || 1));
for (let attempt = 0; attempt < attempts; attempt += 1) { … }
```

而循环里**几乎每个失败分支都会 `continue`**（换号重试）。关键在于
`lib/qoder-shim.mjs:34` 的状态映射：

| 上游 kind | 折成给客户端的码 | routeChat 是否换号重试 |
|---|---|---|
| `soft_rate`（429） | 429 | ✅ continue |
| `hard_credit`（402） | 402 | ✅ continue |
| `session_dead` | — | ✅ continue |
| **`server`（任何 5xx）** | **502** | ❌ return |
| **`not_found`（404）** | **502** | ❌ return |

⚠️ **`502` 这个数字是插件自己造的**：`not_found: 502` 与 `server: 502`
（`lib/qoder-shim.mjs:38-39`）。所以「老是 502」并不等于上游回了 502 ——
它可能是上游 404、也可能是任何 5xx，甚至可能是
`lib/qoder.js:506` 的「上游返回了无法识别的流（无信封帧）」，
或 `lib/qoder.js:535` 的 **catch 到异常**（网络层错误也被折成 502）。

**排查时不要把 502 当成上游状态码**，要拿到 `kind` 才能定性。

叠加效应：本端 3 次换号重试 × 客户端侧因超时重发 = 上游实际调用量是
用户感知的好几倍。

## 问题三：指纹器每次请求都重新提取（48ms，无实例缓存）

`lib/qoder.js:355` 的 `fingerprint()` 用 `fingerprintPromise` 缓存了
**promise**，理论上只构造一次。但实测二次构造同样是 48ms：

```
指纹器首次构造: 48 ms
指纹器二次构造（若有缓存应很快）: 48 ms
```

因为 `createQoderFingerprint()` 每次调用都重新走一遍「从本机 Qoder 安装里
定位并读取 33MB 混淆产物 → 实例化 wasm」。48ms 本身不算灾难，但在
「首字节已经被缓冲拖到 5 秒」的前提下，它属于纯加项。

签名构造成本才是可忽略的（指纹路径 7/1/1ms，手写 COSY 1/0/0ms）——
**签名不是瓶颈**，这一点先排除掉，免得改错地方。

### ① 让流真正流式 —— ✅ 已实施（2026-10-11）

改动落点：

| 文件 | 改动 |
|---|---|
| `lib/qoder-relay.mjs` | 新增 `streamQoderRequest`：边收边回调，**不再等 `end`** |
| `lib/qoder.js` | 新增 `bridgeStream()` / `deferred()`；`routeChat` 改走流式 |

**难点与解法**（这是本次修复的核心，值得记下来）：

难点是「200 但业务失败」的嗅探**必须**先看到内容，而流式又要求尽快交出首字节。
解法是**首帧缓冲**：只等第一帧做判定，通过后立刻返回 stream，剩余帧后台推进。

⚠️ 但这里有一个**必须等首帧再返回**的硬约束，第一版就踩了：

> 一开始写成「立即返回空 stream，转发放到 `void` 后台」，结果首字节**仍是 5.7 秒**。
> 原因是 `routeChat` 不返回，shim 就拿不到 body、无法 `writeHead(200)`。

而「等首帧」还有第二个更重要的理由：shim 一旦拿到 body 就发出响应头了，
**那时首帧若是业务错误，已经无法改成 4xx/5xx** —— 只能把错误混在 200 的流里，
客户端完全看不出。所以首帧判定必须在**返回 stream 之前**完成。

改动后 `bridgeStream` 的 `push` 用「边到边 `enqueue`」，`fail()` 让中途失败以
`error` 结束流（响应头改不了，但能让客户端明确知道这是失败而非空回答）。

### 实测效果

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 客户端首字节 | 5752ms | **356ms** |
| 上游首帧 | 503ms | 503ms（未变，本就不是瓶颈） |
| 分块到达 | 1 块（一次性） | **111 块逐块到达** |
| 总耗时 | 5752ms | 5423ms（流式不改变总时长，只改变感知） |

首字节提升 **16 倍**。总时长基本不变是对的 —— 流式的价值在于「让客户端和用户
尽早看到内容、不再误判超时」，而不是让上游生成得更快。

### 防回归测试

新增 `test/qoder-streaming.test.mjs`（18 项）。关键点：**缓冲实现与流式实现
最终产出的字节完全相同** —— 断言内容、帧数、`[DONE]` 都区分不出两者，
唯一能区分的是**时间**。所以核心用例用「慢速上游」：

> 服务端每帧之间 sleep，断言首帧到达时刻**远早于**服务端发完的时刻。

**已反向验证**：临时给 `streamQoderRequest` 注入「强制缓冲」开关后，
核心用例立刻变红（首帧 1059ms vs 要求 <300ms）；恢复后 18/18 通过。

其余覆盖：首帧业务错误必须拦下且不再转发、非 200 原样带回状态码、
**跨 TCP 分块断帧的拼接**（不做行缓冲会丢字且不报错）、取消时立即停止、
信封解包后传给回调的是 inner 而非外层。

### ②③④ 已实施（2026-10-11 第二轮）

- **② 区分 502 的来源**：每个失败带 `origin`（`business` / `transport` / `internal`），
  shim 另带上游真实码 `upstream`。
- **③ 抑制重复放大**：同一 body 的确定性失败 60s 内只打一次上游。实测 **18 → 1 次**。
  `server` 刻意排除在去重之外（瞬时 5xx 重试有意义）。
- **④ 指纹器缓存**：进程级缓存提取出的 wasm 字节。**38ms → 0-1ms**。
  缓存字节而非实例 —— 实例带可变堆状态，共享会互相污染。

## ⚠️ 本文档的原始判断有一处需要修正

本文把「502」主要归因于 **SSE 全量缓冲 → 首字节过长 → 客户端超时重发**。
那个问题真实存在且已修复（5752ms → 356ms），但它**不是唯一的 502 路径**。

第二轮取证（落盘真实请求体）发现另一条**完全独立**的 502：

> 上游要求「带 `tool_calls` 的 assistant 消息」其 `content` **必须是字符串**。
> pi-ai 在「模型只发工具调用、没有文本」时发 `content: null`，上游因此
> 不认它声明了 tool_calls，紧随的 `tool` 消息失去前置 → **整条请求被拒**。

表现为「**用 qoder 做需要工具的任务必定 502**」，与首字节问题无关。
详见 [qoder-tool-message-502.md](qoder-tool-message-502.md)。

---

## 一句话总结

上游没限流（30 次并发压测零失败）。「502」是插件自造的映射码，背后至少有两条
独立成因，**均已修复**：

1. **SSE 全量缓冲**把首字节拖到整段回复时长 → 客户端超时重发。
   首字节 **5752ms → 356ms**。
2. **`content: null` + `tool_calls`** 被上游判为「未声明工具调用」→ 工具轮次必挂。
   已归一化为空串。

外加两项放大与开销的修复：确定性失败去重（**18 → 1 次上游调用**）、
指纹器字节缓存（**38ms → 1ms**）。
