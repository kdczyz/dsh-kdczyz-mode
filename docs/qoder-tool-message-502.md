# 诊断：Qoder 工具轮次必定 502（`Messages with role 'tool' …`）

排查时间：2026-10-11
现象（用户描述）：「还是出现 502 报错」——**用 qoder 模型做需要工具的任务必定失败**。

## 一句话结论

上游要求 **带 `tool_calls` 的 assistant 消息其 `content` 必须是字符串**；
pi-ai 在「模型只发工具调用、没输出文本」时发的是 `content: null`，
上游因此不认为它声明了 tool_calls，紧随其后的 `tool` 消息失去前置 →
**整条请求被拒**。修复：把这种形状的 `null` 归一成 `""`。

## 为什么之前一直查不到

日志里上游原文**被截断**成：

```
Messages with role 'tool' must b
```

这个残句极易被读成「tool 消息格式不对」，于是排查方向偏到了 tool 消息本身。
实际完整原文（落盘真实请求后拿到）：

```
Messages with role 'tool' must be a response to a preceding message with 'tool_calls'
```

## 定位过程

### 1. 先排除限流

串行 12 次 / 并发 6 路 / 并发 12 路共 30 次压测，**全部 200 **，
零 429、零 5xx。上游从未限流。

### 2. 排除「形状本身不合法」

手写了 **40 多种** tool 消息形状逐一打上游，**全部被接受**：
缺 `tool_call_id`、`content` 为数组/null/空串、只带 `name`、
`arguments` 是对象而非字符串、`tool_call_id` 是数字、缺 `type`、
20 个工具定义、工具名含特殊字符、无 `parameters`、50k 长内容、
tool 出现在最前、多轮工具往返…… 全部 200。

**结论：错误不在 tool 消息的形状上。**

### 3. 落盘真实请求体

给 `routeChat` 加临时落盘（上游一拒绝就写 `/tmp/qoder-dump/`），
复现后拿到 6 份 71KB 的完整请求。三件事立刻清楚：

- 6 份 body-hash **完全相同**（`79bab6b97c7bc925`）→ 失败是**确定性**的；
- 6 份的间隔是 1s / 1.4s / 2.5s / 4.7s / 9s → 这是 **DSH 自己的指数退避重试**；
- `model: "dfmodel"`、27 个工具、13 条消息。

### 4. 二分定位到具体消息

按消息前缀逐段重放：

| 截到第 N 条 | 结果 |
|---|---|
| 前 7 条 | ✅ |
| 前 8 条 | ✅ |
| 前 9 条 | ✅ |
| **前 10 条** | ❌ |
| 前 11 / 13 条 | ❌ |

第 10 条（索引 9）是一条 `tool` 消息。看它的前置（索引 8）：

```json
{ "role": "assistant", "content": null,
  "tool_calls": [ {"id":"call_00_qliw…"}, {"id":"call_01_G3dW…"} ] }
```

而对照组（索引 5→6，**能通过**）：

```json
{ "role": "assistant", "content": "我来看看这个工作区的内容。",
  "tool_calls": [ … ] }
```

**唯一差别就是 `content`：`null` vs 有文本。**

### 5. 决定性验证

只改索引 8 的 `content`，其它一字不动：

| `content` 取值 | 结果 |
|---|---|
| `null`（原样） | ❌ 被拒 |
| `""`（空串） | ✅ **通过** |
| `" "`（空格） | ✅ 通过 |
| **省略该字段** | ❌ 被拒 |

即：**上游要求该字段存在且是字符串**。`null` 和「没有」都不算。

## 根因链

```
模型只发工具调用、没有文本输出
  → pi-ai 发 { role:'assistant', content:null, tool_calls:[…] }
  → 上游不认为这条声明了 tool_calls
  → 其后的 { role:'tool' } 失去前置
  → 整条请求被拒：provider_error
  → 插件折成 502
  → DSH 指数退避重试 6 次 × 插件换号重试 3 次 = 同一 body 打上游 18 次
```

这也解释了「时好时坏」：**带一句说明文字的工具轮次正常，纯工具轮次必挂**。

## 修复

### ① 请求体归一化（根因修复）

`lib/qoder-relay.mjs` 新增 `normalizeQoderPayload()`：

> `role === 'assistant'` 且 `content === null` 且 `tool_calls` 非空 → `content = ''`

- **只改这一种形状**，其余消息逐条透传；
- 纯函数，不改动入参（有测试钉住）；
- 无需改动时返回**原引用**（避免无谓拷贝）；
- 畸形输入一律不抛。

改空串而非占位文案（如 "I have processed…"）是刻意的：
占位文案会把模型没说过的话写进对话历史，下一轮可能被它误导。

**两条构造路径都接了归一化**（`buildQoderChatRequest` 与
`buildQoderFingerprintedRequest`）。这一步必须两边都做 —— 此前故障正是
「指纹路径报错、手写路径正常」，两条路各写各的就会再次分叉。
归一化在**序列化之前**完成，保证签名与 body 用的是同一份文本。

### ② 502 带上真实来源

`not_found` / `server` 都折成 502，只看到 502 无法区分四种来源。
现在每个失败都带 `origin`：

| origin | 含义 |
|---|---|
| `business` | 上游在 HTTP 200 的信封里报的业务错误（本次就是这个） |
| `transport` | 连接层异常，不是上游状态码 |
| `internal` | 本端逻辑抛出 |

shim 的 `writeError` 也会把上游真实状态码作为 `upstream` 一并回传
（只在真有过状态码时才带，不把本端判定伪装成上游结论）。

### ③ 抑制重复放大

同一 body 的**确定性失败**在 60s 窗口内只打一次上游，后续直接回放结论。

| kind | 去重? | 原因 |
|---|---|---|
| `business` / `signature` / `client` | ✅ | 同一 body 必然同样失败 |
| `soft_rate` / `hard_credit` / `session_dead` | ❌ | **换号真的可能成功** |
| `server` | ❌ | 上游 5xx 可能只是瞬时抖动 |

`server` 刻意排除：把它也去重会让一次偶发 5xx 变成一分钟内持续报错 ——
那是把「可恢复」误判成「不可恢复」。测试里专门有一条断言守着这件事
（反向断言：`isDeterministicKind` 的实现体里不得出现 `server`）。

实测效果：**18 次上游调用 → 1 次**。

### ④ 指纹器字节缓存

`createQoderFingerprint()` 每次都要**完整读一遍 33MB 混淆产物**再切出 wasm
（40ms）。新增进程级字节缓存后：**38ms → 0-1ms**。

缓存的是**字节**而非实例：wasm 实例带可变堆状态（`qodercontext_new` 出来的
ctx 是 per-use 的），共享实例会让两次请求互相污染；字节只读，共享无副作用。
只缓存成功结果 —— 提取失败可能只是「本机还没装官方客户端」，不该被永久记住。

## 验证

| 项 | 结果 |
|---|---|
| 落盘的真实失败请求，走指纹路径 | 修复前 **3/3 失败** → 修复后 **3/3 通过** |
| 轻量构造的「content:null + tool_calls」 | HTTP 200，被接受 |
| 三入口注册 | qoder / trae+trae-global / workbuddy-xdpool+global 全齐 |
| 全量测试 | **20 项套件、1330 项断言全绿** |

新增两个测试套件：

- `test/qoder-payload.test.mjs`（24 项）—— 归一化契约。
  关键设计：断言「字段存在**且是 string**」，而不是「不是 null」——
  后者会放过「删掉字段」这种同样错误的做法（实测省略字段也被拒）。
- `test/qoder-dedup.test.mjs`（25 项）—— 去重契约。
  重点在「不该去重的没去」（比「该去重的去了」更容易写错，
  且错了不报错，只表现为「偶发故障变持久故障」）。

两者都做了源码级契约断言，防止 `qoder.js` 里的实现漂移。

## 残留

- 诊断落盘代码已全部移除（`QODER_DUMP*` 零残留）。
- 那份 27 个工具定义的真实请求重放时上游生成极慢（远超 5 分钟），
  未能跑完整轮；核心修复已用等价的轻量请求验证通过。
  这不影响结论 —— 失败与成功只差 `content` 一个字段，已在第 5 步逐值验证。
